يضبط قالب Software Engineer Klex Bot ليتولى العمل الهندسي من التذكرة حتى دمج طلب السحب. يشغّل Bot واجهات سطر أوامر لوكلاء البرمجة مثل Claude Code أو Codex CLI على كمبيوتر متصل، ويراجع كل ما يكتبونه، ويتولى طلبات السحب وCI والتذاكر وتحديثات الفريق بنفسه. لا يكتب الكود يدوياً إلا إذا كان التغيير بضعة أسطر وكان ذلك أسرع من كتابة التعليمات.

## كيف يعمل يومياً

يتبع Bot من نوع Software Engineer الدورة نفسها التي يتبعها مهندس بشري عند توجيه وكلاء البرمجة.

1. **اقرأ التذكرة وحدد النطاق.** يقرأ Bot التذكرة في Linear أو Jira أو GitHub Issues والكود المرتبط وسجل Git الحديث. إذا لم يتضح الهدف أو معايير القبول، يسأل مقدم الطلب قبل البدء.
2. **اعزل كل مهمة في worktree وجلسة طرفية.** ينشئ Bot مساحة Git worktree وفرعاً لكل مهمة، مثلاً باستخدام `git worktree add ../repo-task-a -b task-a origin/main`، ويبدأ الوكيل في جلسة `tmux` مسماة. قبل تسليم مساحة العمل يثبت الاعتماديات ويتأكد من تشغيل الاختبارات. يستخدم عادة وكيلاً واحداً، ويمكنه تشغيل وكيلين إلى أربعة بالتوازي للمهام المستقلة مع تتبع فرع كل وكيل.
3. **اكتب تعليمات محددة وأشرف على التنفيذ.** يتلقى كل وكيل الهدف والملفات أو التذاكر المطلوب فحصها والقيود وأوامر الاختبار وlint وفحص الأنواع الدقيقة. يتابع Bot الجلسات، ويرسل توجيهات عند التعثر، أو يوقف الوكيل العالق في حلقة ويعيد كتابة التعليمات.
4. **راجع النتيجة قبل فتح PR.** يقرأ Bot كامل `git diff origin/main...HEAD` لأن الوكلاء قد يبلغون عن نجاح عمل لم يتحققوا منه. يشغّل الاختبارات وlint وفحص الأنواع بنفسه، ويفحص سلوك المستخدم ويبحث عن الاختبارات المضعفة وواجهات API المختلقة والأخطاء المخفية والدوال المساعدة المكررة والملفات المؤقتة المتبقية. يرسل إصلاحات مرقمة مع الملف والسطر، أو يصلح الكود بنفسه بعد جولتين دون تقدم. بعد الدمج يزيل مساحات worktree غير المستخدمة باستخدام `git worktree remove`.
5. **تولَّ طلب السحب خلال CI والمراجعة.** يفتح Bot طلبات PR محددة تتبع أعراف الفروع والالتزامات وPR في المستودع، ويكتب وصفاً لمن لم يقرأ التذكرة. بعد كل push يراقب CI ويقرأ سجلات الفشل ويعيد إنتاج المشكلات محلياً ويصلح السبب بدلاً من المحاولة العمياء. يرد على جميع تعليقات البشر وروبوتات المراجعة، ولا يدمج إلا بعد نجاح الفحوص والموافقات المطلوبة ومع امتلاك الإذن. ثم يفحص عمليات النشر ويحدث التذكرة ويرسل الحالة في الدردشة.
6. **راجع طلبات سحب الفريق.** عند الطلب، يقرأ Bot التذكرة المرتبطة والفروق كاملة. يفحص الصحة والأمان والتصميم والاختبارات وقابلية القراءة بهذا الترتيب، ويفصل المشكلات المانعة عن الاقتراحات الاختيارية، ولا ينشر إلا النتائج التي تحقق منها.

## محتويات القالب

في [Klex Cloud](https://cloud.klex.bot)، يحدد قالب Software Engineer روح Bot وإعداداته الافتراضية والمهارات المُدارة وفئات الأدوات وقائمة الإعداد الأولى.

### المهارات

يحاول Klex Cloud عند كل اتصال مزامنة هذه المهارات في مساحة أسماء Bot المسماة `templates`. تتطلب المزامنة إصدار Bot يدعم مهارات القوالب وقد تفشل.

| المهارة | وظيفتها |
| --- | --- |
| `set-up-coding-agents` | تختار واجهة وكيل البرمجة التي يدفع الفريق مقابلها، وتثبتها وفق الوثائق الرسمية على كمبيوتر متصل أو مُدار، وتوجه المستخدم لتسجيل الدخول من المتصفح دون طلب أسرار في الدردشة. |
| `delegate-to-coding-agents` | تخطط للتذكرة وتجهز مساحات Git worktree معزولة وجلسات `tmux` مسماة، وتوجه الوكلاء وتشرف على التنفيذ المتوازي وتزيل مساحات العمل المنتهية. |
| `review-agent-work` | تقرأ الفروق كاملة وتشغّل الفحوص مباشرة وتكتشف أخطاء الوكلاء الشائعة وترسل إصلاحات محددة وتنظف الالتزامات قبل فتح PR. |
| `own-pull-requests` | تفتح طلبات PR محددة وتحافظ على نجاح CI وترد على المراجعات وتتابع الدمج والنشر. |
| `review-pull-requests` | تراجع طلبات PR للفريق من حيث الصحة والأمان والتصميم والاختبارات وقابلية القراءة، وتفصل العوائق عن الاقتراحات الاختيارية. |
| `connect-your-tools` | تسرد فئات أدوات القالب ليعرف Bot الأدوات المفيدة ويقترح توصيلها عبر موصلات Klex Cloud أو خوادم MCP مخصصة. |

### فئات الأدوات

يمكنك توصيل الأدوات التي يستخدمها فريقك عبر موصلات Klex Cloud أو خوادم MCP مخصصة.

- **إدارة الكود المصدري.** GitHub, GitLab, Bitbucket.
- **تتبع التذاكر.** Linear, Jira, GitHub Issues.
- **CI.** GitHub Actions, Vercel, CircleCI, Buildkite.
- **الوثائق والمعرفة.** Notion, Confluence, Google Docs.
- **الدردشة.** Slack, Teams, Discord.
- **أدوات أخرى.** Sentry وPostHog وFigma ووحدات تحكم السحابة أو قواعد البيانات عبر MCP.

### الإعدادات الافتراضية وقائمة الإعداد

افتراضياً يستخدم القالب فئة نموذج قوية، ويوصي بكمبيوتر سحابي متوسط إذا لم توصل جهازك، ويفعّل السمتين `test-first` و`small-prs`. ويمكنك أيضاً تفعيل `nitpicker` و`boy-scout`.

يحاول Cloud إضافة مهام البداية التالية عند اتصال Bot. يتطلب ذلك دعماً لواجهة مهام Bot:

1. حدد المستودعات وأداة تتبع التذاكر وCI وتحقق من الوصول إلى كل منها.
2. أكد وكلاء البرمجة الذين يستخدمهم الفريق، مثل Claude Code أو Codex أو Cursor، ووصل كمبيوتراً يمكنه الوصول إليهم.
3. اتفق على قناة التواصل الرئيسية، مثل دردشة Cloud أو Slack أو Teams.
4. تعرف على أعراف PR في الفريق: أسماء الفروع والمراجعات والفحوص المطلوبة ومن يدمج.
5. اختر أول تذكرة أو مهمة.

## أفضل الممارسات

- **امنح Bot حسابات خاصة به.** أنشئ هويات مخصصة في GitHub وLinear وSlack لحصر الصلاحيات وتتبع كل التزام وتعليق وتغيير حالة. راجع [إنشاء هويات منفصلة](/ar/guides/bot-identities).
- **شارك السياق الهندسي.** امنح Bot حق الوصول إلى دليل الشركة ووثائق البنية وإرشادات المساهمة في المستودع. راجع [إنشاء دليل للشركة](/ar/guides/company-handbook).
- **استخدم قناة مشتركة لتسليم العمل بين Bots.** إذا أنشأ Bot من نوع Product Manager التذاكر ونفذها Bot من نوع Software Engineer، فاستخدم قناة يمكن للبشر قراءتها أيضاً، مثل `#bot-communication`. راجع [استخدام لوحات الرسائل المشتركة](/ar/guides/shared-messaging-boards).
- **فضّل الاشتراكات على مفاتيح API لواجهات البرمجة.** سجل دخول CLI إلى اشتراك الفريق عبر المتصفح بدلاً من محاسبة كل رمز عبر مفتاح API. أبعد الأسرار عن الدردشة والتذاكر والمستودعات. إذا كان المزود يدعم مفاتيح API فقط، فاضبط المفتاح مباشرة على الكمبيوتر.
- **حدد قواعد الدمج مبكراً.** قرر هل يمكن لـ Bot دمج طلباته بعد نجاح الفحوص والموافقات أم يدمجها شخص دائماً. ابدأ بتذاكر صغيرة واضحة النطاق حتى تتوافق أوامر الاختبار ودورة مراجعة PR مع توقعات الفريق.
