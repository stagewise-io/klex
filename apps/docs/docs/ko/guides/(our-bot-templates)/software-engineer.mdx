Software Engineer 템플릿은 티켓부터 병합된 풀 리퀘스트까지 개발 작업을 맡도록 Klex Bot을 설정합니다. Bot은 연결된 컴퓨터에서 Claude Code나 Codex CLI 같은 코딩 에이전트 CLI를 실행하고 작성된 모든 결과를 검토하며, 풀 리퀘스트, CI, 티켓과 팀 업데이트를 직접 처리합니다. 변경이 몇 줄에 불과하고 지시문 작성보다 빠를 때만 직접 코드를 작성합니다.

<Panel title="알아두기">
Bot 템플릿은 [Klex Cloud](https://cloud.klex.bot)에서 관리합니다. Klex Cloud 없이 Klex를 자체 호스팅한다면 MCP로 컴퓨터를 연결하고 Bot 데이터 디렉터리에 동등한 Agent Skills를 추가해 같은 흐름을 사용할 수 있습니다.
</Panel>

## 일상적인 작업 방식

Software Engineer Bot은 사람이 코딩 에이전트를 지휘할 때와 같은 순서로 작업합니다.

1. **티켓을 읽고 범위를 명확히 합니다.** Bot은 Linear, Jira 또는 GitHub Issues의 티켓과 관련 코드, 최근 Git 기록을 읽습니다. 목표나 수락 기준이 불명확하면 시작 전에 요청자에게 묻습니다.
2. **각 작업을 worktree와 터미널 세션으로 분리합니다.** 작업마다 Git worktree와 브랜치를 만들고, 예를 들어 `git worktree add ../repo-task-a -b task-a origin/main`를 사용합니다. 이름이 있는 `tmux` 세션에서 에이전트를 시작하고 전달 전에 의존성을 설치하고 테스트 실행을 확인합니다. 보통 에이전트 하나를 사용하지만 독립된 작업이 여러 개면 두 개에서 네 개를 병렬로 실행하고 각 브랜치를 추적할 수 있습니다.
3. **구체적인 지시를 작성하고 감독합니다.** 각 에이전트에 목표, 살펴볼 파일이나 티켓, 제약 조건과 정확한 테스트·린트·타입 검사 명령을 전달합니다. Bot은 세션을 확인하고 정체되면 추가 지시를 보내며 반복에 빠지면 중지하고 지시를 다시 씁니다.
4. **PR을 열기 전에 결과를 검토합니다.** 에이전트가 검증하지 않은 작업을 성공했다고 보고할 수 있으므로 Bot은 `git diff origin/main...HEAD` 전체를 읽습니다. 직접 테스트, 린트, 타입 검사를 실행하고 사용자 동작과 약화된 테스트, 지어낸 API, 무시된 오류, 중복 헬퍼, 남은 임시 파일을 확인합니다. 문제가 있으면 파일과 줄을 포함한 번호 매긴 수정을 보내고 두 차례 진전이 없으면 직접 수정합니다. 통합 후 `git worktree remove`로 사용하지 않는 worktree를 제거합니다.
5. **CI와 리뷰 전반에서 풀 리퀘스트를 담당합니다.** 저장소의 브랜치, 커밋, PR 규칙에 맞춰 범위가 명확한 PR을 열고 티켓을 읽지 않은 리뷰어를 위해 설명합니다. 매 push 후 CI와 실패 로그를 살피고 문제를 로컬에서 재현해 원인을 고칩니다. 사람과 리뷰 봇의 모든 댓글에 답하고 필수 검사와 승인, 병합 권한이 있을 때만 병합합니다. 배포를 확인하고 티켓을 갱신하며 채팅에 상태를 알립니다.
6. **팀원의 풀 리퀘스트를 리뷰합니다.** 요청받으면 연결된 티켓과 전체 diff를 읽고 정확성, 안전성, 설계, 테스트, 가독성을 순서대로 확인합니다. 차단 문제와 선택적 제안을 구분하고 확인한 내용만 게시합니다.

## 템플릿 구성

[Klex Cloud](https://cloud.klex.bot)의 Software Engineer 템플릿은 Bot의 soul, 기본값, 관리형 skills, 도구 범주와 첫 온보딩 체크리스트를 설정합니다.

### Skills

Klex Cloud는 Bot이 연결될 때마다 이 skills를 Bot의 `templates` 네임스페이스에 동기화하려고 시도합니다. template skills를 지원하는 Bot 버전이 필요하며 동기화가 실패할 수 있습니다.

| Skill | 역할 |
| --- | --- |
| `set-up-coding-agents` | 팀이 결제하는 코딩 에이전트 CLI를 선택하고 공식 문서에 따라 연결되었거나 관리되는 컴퓨터에 설치하며, 채팅에서 비밀을 요구하지 않고 브라우저 로그인을 안내합니다. |
| `delegate-to-coding-agents` | 티켓을 계획하고 분리된 Git worktree와 이름 있는 `tmux` 세션을 준비하며 에이전트에 지시하고 병렬 실행을 감독한 뒤 완료된 worktree를 제거합니다. |
| `review-agent-work` | 전체 diff를 읽고 검사를 직접 실행하며 흔한 오류를 찾아 구체적인 수정을 보내고 PR 전에 커밋을 정리합니다. |
| `own-pull-requests` | 범위가 명확한 PR을 열고 CI를 정상으로 유지하며 리뷰에 답하고 병합과 배포까지 추적합니다. |
| `review-pull-requests` | 팀 PR의 정확성, 안전성, 설계, 테스트, 가독성을 검토하고 차단 문제와 선택적 제안을 구분합니다. |
| `connect-your-tools` | 템플릿의 도구 범주를 나열해 Bot이 유용한 도구를 파악하고 Klex Cloud 커넥터나 사용자 지정 MCP 서버 연결을 제안할 수 있게 합니다. |

### 도구 범주

Klex Cloud 커넥터 또는 사용자 지정 MCP 서버를 통해 팀이 이미 사용하는 도구를 연결할 수 있습니다.

- **소스 관리.** GitHub, GitLab, Bitbucket.
- **이슈 추적.** Linear, Jira, GitHub Issues.
- **CI.** GitHub Actions, Vercel, CircleCI, Buildkite.
- **문서와 지식.** Notion, Confluence, Google Docs.
- **채팅.** Slack, Teams, Discord.
- **기타 도구.** Sentry, PostHog, Figma, 클라우드 콘솔 또는 MCP를 통한 데이터베이스.

### 기본값과 온보딩 체크리스트

기본적으로 템플릿은 강력한 모델 등급을 사용하고, 자체 컴퓨터를 연결하지 않으면 중간 규모의 클라우드 컴퓨터를 권장하며, `test-first`와 `small-prs` 특성을 활성화합니다. `nitpicker`와 `boy-scout`도 활성화할 수 있습니다.

Cloud는 Bot이 연결될 때 다음 초기 할 일을 추가하려고 시도합니다. Bot이 todos API를 지원해야 합니다:

1. 사용하는 저장소, 이슈 추적 도구, CI를 파악하고 각각의 접근 권한을 확인합니다.
2. Claude Code, Codex, Cursor 등 팀의 코딩 에이전트를 확인하고 접근 가능한 컴퓨터를 연결합니다.
3. Cloud 채팅, Slack, Teams 등 주요 소통 채널을 정합니다.
4. 브랜치 이름, 필수 리뷰와 검사, 병합 담당자 등 팀의 PR 규칙을 배웁니다.
5. 첫 이슈나 작업을 선택합니다.

## 권장 사항

- **Bot에 전용 계정을 부여합니다.** GitHub, Linear, Slack 전용 계정을 만들어 권한을 제한하고 각 커밋, 댓글, 상태 변경을 추적합니다. [별도 계정 만들기](/ko/guides/bot-identities)를 참조하세요.
- **개발 맥락을 공유합니다.** 회사 핸드북, 아키텍처 문서, 저장소 기여 가이드에 대한 접근을 Bot에 부여합니다. [회사 핸드북 만들기](/ko/guides/company-handbook)를 참조하세요.
- **Bot 간 인계에 공유 채널을 사용합니다.** Product Manager Bot이 티켓을 만들고 Software Engineer Bot이 구현한다면 `#bot-communication`처럼 사람도 읽을 수 있는 채널을 사용합니다. [공유 메시지 보드 사용](/ko/guides/shared-messaging-boards)을 참조하세요.
- **코딩 CLI에는 API 키보다 구독을 우선합니다.** API 키로 토큰마다 비용을 청구하는 대신 브라우저에서 팀 구독으로 CLI에 로그인합니다. 채팅, 티켓, 저장소에 비밀을 남기지 마세요. 제공업체가 API 키만 지원하면 컴퓨터에 직접 키를 설정합니다.
- **병합 규칙을 일찍 정합니다.** 검사와 승인 후 Bot이 자신의 PR을 병합할 수 있는지, 항상 사람이 병합할지 결정합니다. 테스트 명령과 PR 리뷰 흐름이 팀의 기대에 맞을 때까지 작고 범위가 명확한 티켓부터 시작합니다.
