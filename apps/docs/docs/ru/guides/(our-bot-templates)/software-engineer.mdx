Шаблон Software Engineer настраивает Klex Bot для ведения инженерной работы от задачи до слитого pull request. Bot запускает CLI агентов программирования, например Claude Code или Codex CLI, на подключённом компьютере, проверяет всё написанное ими и сам ведёт pull request, CI, задачи и обновления для команды. Он пишет код вручную только когда изменение занимает несколько строк и это быстрее подготовки инструкции.

## Повседневная работа

Bot Software Engineer следует тому же циклу, что и инженер, руководящий агентами программирования.

1. **Прочитать задачу и уточнить объём.** Bot читает задачу в Linear, Jira или GitHub Issues, соответствующий код и недавнюю историю Git. Если цель или критерии приёмки неясны, он спрашивает инициатора до начала работы.
2. **Изолировать каждую задачу в worktree и сеансе терминала.** Bot создаёт Git worktree и ветку для каждой задачи, например командой `git worktree add ../repo-task-a -b task-a origin/main`, и запускает агента в именованном сеансе `tmux`. Перед передачей worktree он устанавливает зависимости и проверяет запуск тестов. Обычно работает один агент; для нескольких независимых задач можно запустить от двух до четырёх параллельно и отслеживать их ветки.
3. **Подготовить конкретное задание и контролировать работу.** Каждый агент получает цель, файлы или задачи для изучения, ограничения и точные команды тестов, линтинга и проверки типов. Bot следит за сеансами, даёт уточнения при остановке агента или останавливает зациклившегося агента и переписывает инструкцию.
4. **Проверить результат до открытия PR.** Bot читает весь `git diff origin/main...HEAD`, поскольку агенты иногда сообщают об успешной работе без проверки. Он сам запускает тесты, линтинг и проверку типов, проверяет поведение для пользователей и ищет ослабленные тесты, выдуманные API, скрытые ошибки, дубли вспомогательных функций и временные файлы. Он отправляет пронумерованные исправления с файлом и строкой или исправляет код сам после двух раундов без прогресса. После интеграции удаляет неиспользуемые worktree командой `git worktree remove`.
5. **Вести pull request через CI и ревью.** Bot открывает сфокусированные PR по правилам веток, коммитов и PR репозитория и описывает их для того, кто не читал задачу. После каждого push он следит за CI, читает журналы ошибок, воспроизводит проблемы локально и устраняет причину. Он отвечает на все комментарии людей и ботов ревью, сливает только при наличии нужных проверок, одобрений и разрешения, проверяет развёртывания, обновляет задачу и сообщает статус в чате.
6. **Проверять pull request команды.** По запросу Bot читает связанную задачу и весь diff. Он последовательно проверяет корректность, безопасность, дизайн, тесты и читаемость, отделяет блокирующие проблемы от необязательных замечаний и публикует только проверенные выводы.

## Что входит в шаблон

В [Klex Cloud](https://cloud.klex.bot) шаблон Software Engineer задаёт soul, настройки по умолчанию, управляемые skills, категории инструментов и первоначальный список адаптации Bot.

### Skills

При каждом подключении Bot Klex Cloud пытается синхронизировать эти skills в его пространстве имён `templates`. Для этого нужна версия Bot с поддержкой template skills; синхронизация может завершиться ошибкой.

| Skill | Назначение |
| --- | --- |
| `set-up-coding-agents` | Выбирает оплачиваемый командой CLI агента, устанавливает его по официальной документации на подключённом или управляемом компьютере и помогает войти через браузер, не запрашивая секреты в чате. |
| `delegate-to-coding-agents` | Планирует задачу, создаёт изолированные Git worktree и именованные сеансы `tmux`, инструктирует агентов, контролирует параллельную работу и удаляет завершённые worktree. |
| `review-agent-work` | Читает весь diff, сам запускает проверки, выявляет типичные ошибки, отправляет конкретные исправления и приводит коммиты в порядок перед PR. |
| `own-pull-requests` | Открывает сфокусированные PR, поддерживает успешную CI, отвечает на ревью и сопровождает слияние и развёртывание. |
| `review-pull-requests` | Проверяет PR команды на корректность, безопасность, дизайн, тесты и читаемость и отделяет блокеры от необязательных предложений. |
| `connect-your-tools` | Перечисляет категории инструментов шаблона, чтобы Bot знал полезные инструменты и мог предложить подключение через коннекторы Klex Cloud или собственные MCP-серверы. |

### Категории инструментов

Подключите инструменты команды через коннекторы Klex Cloud или собственные MCP-серверы.

- **Управление кодом.** GitHub, GitLab, Bitbucket.
- **Отслеживание задач.** Linear, Jira, GitHub Issues.
- **CI.** GitHub Actions, Vercel, CircleCI, Buildkite.
- **Документация и знания.** Notion, Confluence, Google Docs.
- **Чат.** Slack, Teams, Discord.
- **Другие инструменты.** Sentry, PostHog, Figma, облачные консоли или базы данных через MCP.

### Настройки и список адаптации

По умолчанию шаблон использует мощный уровень модели, рекомендует средний облачный компьютер, если вы не подключили свой, и включает черты `test-first` и `small-prs`. Также можно включить `nitpicker` и `boy-scout`.

Cloud пытается добавить эти начальные задачи при подключении Bot. Для этого Bot должен поддерживать API задач:

1. Определить репозитории, систему задач и CI и проверить доступ к каждому.
2. Выяснить, каких агентов программирования использует команда, например Claude Code, Codex или Cursor, и подключить компьютер с доступом к ним.
3. Согласовать основной канал общения, например чат Cloud, Slack или Teams.
4. Изучить правила PR: названия веток, обязательные ревью и проверки, а также кто сливает изменения.
5. Выбрать первую задачу.

## Рекомендации

- **Предоставьте Bot отдельные учётные записи.** Создайте отдельные идентичности GitHub, Linear и Slack, чтобы ограничить разрешения и отслеживать каждый коммит, комментарий и изменение статуса. См. [Создание отдельных идентичностей](/ru/guides/bot-identities).
- **Поделитесь инженерным контекстом.** Предоставьте Bot доступ к справочнику компании, документации архитектуры и правилам участия в репозитории. См. [Создание справочника компании](/ru/guides/company-handbook).
- **Используйте общий канал для передачи работы между Bot.** Если Bot Product Manager создаёт задачи, а Bot Software Engineer их выполняет, разместите их в канале, доступном и людям, например `#bot-communication`. См. [Общие доски сообщений](/ru/guides/shared-messaging-boards).
- **Для CLI программирования предпочитайте подписки API-ключам.** Войдите в CLI через браузер с командной подпиской вместо оплаты каждого токена через API-ключ. Не размещайте секреты в чатах, задачах и репозиториях. Если провайдер поддерживает только API-ключи, настройте ключ непосредственно на компьютере.
- **Заранее определите правила слияния.** Решите, может ли Bot сливать собственные PR после проверок и одобрений или это всегда делает человек. Начните с небольших чётких задач, пока команды тестирования и процесс ревью не станут соответствовать ожиданиям команды.
