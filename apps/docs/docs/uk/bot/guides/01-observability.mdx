На [панелі Klex Cloud](https://cloud.klex.bot) можна бачити, що робить бот, і спілкуватися з ним.

Адміністратори також можуть переглядати чати та навички бота через його Admin API. Панель Cloud надає інтерфейс до Admin API кожного бота. Де зберігаються ці дані, див. у розділі [каталог даних](/uk/bot/concepts/data-directory).

<a id="review-activity-and-diagnostics"></a>

## Перегляд активності та діагностики

<Tabs syncKey="hosting" hash={false}>
<Tab title="Хостинг у Cloud">

У Klex Cloud відкрийте бота та виберіть **Activity**, щоб переглянути його нещодавню роботу. Виберіть дію, щоб побачити подробиці, а для перегляду старіших дій, якщо вони доступні, використовуйте **Load older activity**. Перегляд активності може не містити всіх попередніх подій.

</Tab>
<Tab title="Власний хостинг">

<a id="check-self-hosted-diagnostics"></a>

В інтерактивному застосунку Klex відкрийте **Settings → Logs**, щоб переглянути останні журнали виконання. Стрілками прокручуйте записи, `l` змінює мінімальний відображуваний рівень, а `v` — стиль відображення. Зміна рівня відображення не обов’язково вмикає збирання додаткових журналів.

Переглядач зберігає в пам’яті до 500 захоплених записів поточного процесу, тому старіші записи можуть бути недоступні. Журнали виконання не є повним записом розмов бота або результатів завдань. У режимі headless Klex записує журнали в консоль замість інтерактивного переглядача.

Для відомостей про версію та підключення відкрийте **Settings → Debug Information**. Тут показано версію Klex, каталог даних і, якщо доступно, стан реєстрації в Cloud та тунелю. Перед поширенням перевірте журнали й діагностику на конфіденційну інформацію.

</Tab>
</Tabs>

<a id="if-a-bot-does-not-respond"></a>

## Якщо бот не відповідає

Перевірте кожну частину шляху, починаючи з бота й закінчуючи джерелом повідомлення:

1. **Перевірте, чи працює бот.** Для бота на власному хостингу перевірте його процес або службу. Якщо ввімкнено необов’язковий listener стану, перевірте його endpoint готовності. Успішна перевірка не доводить, що модель або підключення працюють.
2. **Перевірте доступ до моделі.** Переконайтеся, що провайдера налаштовано та вибрано модель чату. Якщо запити не проходять, перевірте обліковий запис і службу провайдера. Див. [Моделі](/uk/bot/concepts/models).
3. **Перевірте підключення й обліковий запис.** Для повідомлення з підключеного застосунку перевірте стан MCP-сервера, потрібну авторизацію та доступ облікового запису бота до розмови. Доставка подій також залежить від можливостей сервера. Див. [MCP і боти Klex](/uk/bot/concepts/mcp#if-a-connection-needs-attention).
4. **Перегляньте доступну активність і журнали.** Шукайте помилки приблизно під час запиту. Скористайтеся панеллю Cloud, якщо вона доступна, або наведеною вище діагностикою власного хостингу. Журнали й активність можуть бути неповними; відсутній запис сам по собі не визначає місце збою доставки.

Перед поширенням перевірте діагностику на конфіденційну інформацію. Не включайте облікові дані до запиту в підтримку.

<a id="review-activity-with-the-admin-api"></a>

## Перегляд активності через Admin API

Адміністратори, які використовують Admin API, можуть:

- Отримати список збережених екземплярів сесій через `GET /v1/sessions`, а потім повідомлення сесії через `GET /v1/sessions/{instanceId}/messages`. Використовуйте `nextCursor` для отримання старіших сторінок. Деякі старі повідомлення могли бути обрізані; перевірте `trimmedMessageCount`.
- Переглянути поточну активність сесій через `GET /v1/introspect/sessions`. Дані можуть включати `childSessions`, наприклад активні сесії пошуку чи запису пам’яті або консультації. Завершені дочірні сесії пропущено, тому це не повна історія.
- Запитати записане використання викликів моделі через `GET /v1/usage`. Результати можна групувати за моделлю або провайдером та агрегувати за часом. Загальна кількість токенів може бути неповною, якщо провайдер не повідомляє використання; перевірте `tokenUsageUnreportedCount`.

Використовуйте `GET /v1/openapi.json` для перегляду доступних маршрутів і параметрів запиту API. Повідомлення сесій і вивід інструментів можуть містити конфіденційну інформацію; обмежте коло осіб, які можуть їх переглядати та зберігати.

<a id="access-activity-data"></a>

### Доступ до даних активності

<Tabs syncKey="hosting" hash={false}>
<Tab title="Хостинг у Cloud">

Використовуйте панель Klex Cloud для перегляду активності бота та спілкування з ним. Локальний listener нижче призначений для ботів на власному хостингу.

</Tab>
<Tab title="Власний хостинг">

<a id="access-the-local-admin-api"></a>

Застосунок на власному хостингу типово не відкриває локальний порт Admin API. Його необов’язковий listener прив’язаний до `127.0.0.1` і **не має автентифікації**. Будь-хто, хто може до нього підключитися, включно з іншими локальними користувачами й процесами, може отримати конфіденційні дані бота та використовувати маршрути керування. Вмикайте його лише там, де цим користувачам і процесам довіряють; не відкривайте й не переадресовуйте його в недовірену мережу.

Наприклад, щоб запустити наявного бота в режимі headless з увімкненим локальним listener:

~~~sh
klex --headless --data-dir /path/to/bot --dangerous-local-admin-api-port 2706
~~~

Замініть шлях і порт власними значеннями. На тому самому комп’ютері можна переглянути доступні маршрути:

~~~sh
curl http://127.0.0.1:2706/v1/openapi.json
~~~

Порт також можна задати через `KLEX_DANGEROUS_LOCAL_ADMIN_API_PORT`; параметр командного рядка має пріоритет. Після завершення зупиніть бота та перезапустіть його без параметра або змінної середовища, щоб вимкнути listener.

</Tab>
</Tabs>

Щоб зупинити бота або змінити його підключений доступ, див. [Керування ботом Klex](/uk/bot/guides/control-and-limits).
