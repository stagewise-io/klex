Шаблон Software Engineer налаштовує Klex Bot для ведення інженерної роботи від завдання до злитого pull request. Bot запускає CLI агентів програмування, як-от Claude Code або Codex CLI, на підключеному комп’ютері, перевіряє все написане ними та сам веде pull request, CI, завдання й оновлення для команди. Він пише код вручну лише тоді, коли зміна складається з кількох рядків і це швидше за написання інструкції.

## Щоденна робота

Bot Software Engineer дотримується того самого циклу, що й інженер, який керує агентами програмування.

1. **Прочитати завдання та уточнити обсяг.** Bot читає завдання в Linear, Jira або GitHub Issues, відповідний код та недавню історію Git. Якщо мета чи критерії прийняття незрозумілі, він запитує замовника до початку роботи.
2. **Ізолювати кожне завдання у worktree та сеансі термінала.** Bot створює Git worktree і гілку для кожного завдання, наприклад командою `git worktree add ../repo-task-a -b task-a origin/main`, і запускає агента в іменованому сеансі `tmux`. Перед передачею worktree він установлює залежності та перевіряє запуск тестів. Зазвичай працює один агент; для кількох незалежних завдань можна запустити від двох до чотирьох паралельно, відстежуючи їхні гілки.
3. **Написати конкретне завдання й наглядати.** Кожен агент отримує мету, файли або завдання для перевірки, обмеження та точні команди тестів, лінтингу й перевірки типів. Bot стежить за сеансами, уточнює роботу агента, що зупинився, або зупиняє агента в циклі й переписує інструкцію.
4. **Перевірити результат перед PR.** Bot читає весь `git diff origin/main...HEAD`, бо агенти іноді повідомляють про успіх без перевірки. Він сам запускає тести, лінтинг і перевірку типів, перевіряє поведінку для користувачів і шукає послаблені тести, вигадані API, приховані помилки, дублікати допоміжних функцій і тимчасові файли. Він надсилає нумеровані виправлення з файлами та рядками або виправляє код сам після двох раундів без прогресу. Після інтеграції видаляє невикористані worktree командою `git worktree remove`.
5. **Вести pull request через CI та рев’ю.** Bot відкриває сфокусовані PR за правилами гілок, комітів і PR репозиторію та описує їх для того, хто не читав завдання. Після кожного push він стежить за CI, читає журнали помилок, відтворює проблеми локально та усуває причину. Він відповідає на всі коментарі людей і ботів рев’ю, зливає лише за наявності потрібних перевірок, схвалень і дозволу, перевіряє розгортання, оновлює завдання й повідомляє статус у чаті.
6. **Перевіряти pull request команди.** На запит Bot читає пов’язане завдання та весь diff. Він перевіряє послідовно правильність, безпеку, дизайн, тести та читабельність, відокремлює блокувальні проблеми від необов’язкових зауважень і публікує лише перевірені висновки.

## Що містить шаблон

У [Klex Cloud](https://cloud.klex.bot) шаблон Software Engineer визначає soul, типові налаштування, керовані skills, категорії інструментів і початковий список адаптації Bot.

### Skills

За кожного підключення Bot Klex Cloud намагається синхронізувати ці skills у його просторі імен `templates`. Для цього потрібна версія Bot із підтримкою template skills; синхронізація може не вдатися.

| Skill | Призначення |
| --- | --- |
| `set-up-coding-agents` | Обирає оплачуваний командою CLI агента, встановлює його за офіційною документацією на підключеному або керованому комп’ютері та допомагає увійти через браузер, не запитуючи секретів у чаті. |
| `delegate-to-coding-agents` | Планує завдання, створює ізольовані Git worktree та іменовані сеанси `tmux`, інструктує агентів, наглядає за паралельною роботою і видаляє завершені worktree. |
| `review-agent-work` | Читає весь diff, сам запускає перевірки, знаходить типові помилки, надсилає конкретні виправлення та впорядковує коміти перед PR. |
| `own-pull-requests` | Відкриває сфокусовані PR, підтримує успішну CI, відповідає на рев’ю та супроводжує злиття й розгортання. |
| `review-pull-requests` | Перевіряє PR команди на правильність, безпеку, дизайн, тести й читабельність та відокремлює блокери від необов’язкових пропозицій. |
| `connect-your-tools` | Перелічує категорії інструментів шаблону, щоб Bot знав корисні інструменти та міг запропонувати підключення через конектори Klex Cloud або власні MCP-сервери. |

### Категорії інструментів

Підключіть інструменти команди через конектори Klex Cloud або власні MCP-сервери.

- **Керування кодом.** GitHub, GitLab, Bitbucket.
- **Відстеження завдань.** Linear, Jira, GitHub Issues.
- **CI.** GitHub Actions, Vercel, CircleCI, Buildkite.
- **Документація та знання.** Notion, Confluence, Google Docs.
- **Чат.** Slack, Teams, Discord.
- **Інші інструменти.** Sentry, PostHog, Figma, хмарні консолі або бази даних через MCP.

### Типові налаштування та список адаптації

За замовчуванням шаблон використовує потужний рівень моделі, рекомендує середній хмарний комп’ютер, якщо ви не підключили власний, і вмикає риси `test-first` та `small-prs`. Також можна ввімкнути `nitpicker` і `boy-scout`.

Cloud намагається додати ці початкові завдання під час підключення Bot. Для цього Bot має підтримувати API завдань:

1. Визначити репозиторії, систему завдань і CI та перевірити доступ до кожного.
2. З’ясувати, яких агентів програмування використовує команда, наприклад Claude Code, Codex або Cursor, і підключити комп’ютер із доступом до них.
3. Узгодити основний канал спілкування, наприклад чат Cloud, Slack або Teams.
4. Вивчити правила PR: назви гілок, потрібні рев’ю й перевірки та хто зливає зміни.
5. Обрати перше завдання.

## Рекомендації

- **Надайте Bot окремі облікові записи.** Створіть окремі ідентичності GitHub, Linear і Slack, щоб обмежити дозволи та відстежувати кожен коміт, коментар і зміну статусу. Див. [Створення окремих ідентичностей](/uk/guides/bot-identities).
- **Поділіться інженерним контекстом.** Надайте Bot доступ до довідника компанії, документації архітектури та правил участі в репозиторії. Див. [Створення довідника компанії](/uk/guides/company-handbook).
- **Використовуйте спільний канал для передачі між Bot.** Якщо Bot Product Manager створює завдання, а Bot Software Engineer виконує їх, розмістіть їх у каналі, доступному також людям, як-от `#bot-communication`. Див. [Спільні дошки повідомлень](/uk/guides/shared-messaging-boards).
- **Для CLI програмування віддавайте перевагу підпискам, а не API-ключам.** Увійдіть у CLI через браузер із командною підпискою замість оплати кожного токена через API-ключ. Не розміщуйте секрети в чатах, завданнях і репозиторіях. Якщо провайдер підтримує лише API-ключі, налаштуйте ключ безпосередньо на комп’ютері.
- **Заздалегідь визначте правила злиття.** Вирішіть, чи може Bot зливати власні PR після перевірок і схвалень, чи це завжди робить людина. Почніть із невеликих чітких завдань, доки команди тестування та процес рев’ю не відповідатимуть очікуванням команди.
